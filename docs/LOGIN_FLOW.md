# Login Flow

## Purpose

This document defines authentication for teams in the KBU Hackathons system.

AI coding agents should treat this document as the source of truth for team login behavior unless the repository contains a newer explicit decision.

---

## 1. Team Authentication Model

Each approved team has exactly one shared Better Auth user account.

Example:

```text
Team
  |
  +-- TeamMember A
  +-- TeamMember B
  +-- TeamMember C
  |
  +-- Better Auth User
        username: kbu-ai-builders
        password: ********
```

Every member of the team uses the same credentials.

There is no separate Better Auth login account for each TeamMember.

---

## 2. Login Credentials

Team login uses:

```text
Username
Password
```

No email login is required for the normal team login flow.

No magic link is required for normal login.

The username is generated by the server from the registration team name.

Example:

```text
Team name:
KBU AI Builders

Team username:
kbu-ai-builders
```

The username is immutable from the team's perspective.

---

## 3. Login Preconditions

A team should be able to log in only when:

- The team exists.
- The registration is approved.
- The team has a linked Better Auth user.
- The account is active/not banned.
- The username exists.
- The password is correct.

Conceptually:

```text
username + password
        |
        v
Better Auth
        |
        v
Find team user
        |
        +-- account inactive/banned --> reject
        |
        +-- password invalid --------> reject
        |
        v
Create authenticated session
        |
        v
Resolve Team from User.team
        |
        v
Team dashboard
```

---

## 4. Username Authentication

Use Better Auth's username/password capability rather than creating a custom password authentication implementation.

The application should use the Better Auth Username plugin if that is the selected authentication configuration.

The server should authenticate through Better Auth.

Do not manually compare passwords in application code.

---

## 5. Session

After successful login:

1. Better Auth creates the session.
2. The authenticated user is loaded from the session.
3. The application resolves the associated Team.
4. Team-only pages/actions verify that the authenticated user has the team role.
5. Team-specific operations use the linked Team ID rather than trusting a Team ID supplied by the client.

Important security rule:

```text
authenticated user -> Team relation -> authorized team data
```

Do not trust:

```text
client-provided teamId
```

for authorization.

---

## 6. Failed Login

Invalid credentials should return a generic authentication failure.

Do not reveal whether:

- the username exists,
- the team exists,
- the account was previously provisioned,
- or the password alone was incorrect.

Avoid leaking sensitive account state through error messages.

---

## 7. Banned / Disabled Team

If an organizer bans or disables the team account:

```text
Existing session
       |
       v
revoked/invalidated
       |
       v
future requests rejected
```

Future username/password login must also fail.

The exact Better Auth ban/session APIs should be used instead of implementing a custom password-blocking mechanism.

---

## 8. Password Reset

Password reset is separate from login.

The recovery email should be the email associated with the team account, initially based on the team leader's submitted email.

Password reset can be triggered by:

- The team via the `/api/password-reset/request` endpoint with their `username`.
- An organizer/admin via the `resetTeamPassword` server action.

Both paths send a password-reset email to the verified team leader's email address.

The leader follows the link and chooses a new team password.

Do not use the student verification token for password reset.

Do not use the student verification token as a login token.

---

## 9. Leader / Recovery Email

The team account has a recovery/contact email.

Current product rules do not provide a normal leader-promotion flow.

If leader changes are introduced later, the account recovery email must also be updated safely and audited.

Do not silently change authentication ownership because a TeamMember record changed.

---

## 10. Logout

Normal logout should use Better Auth's session/sign-out functionality.

No custom token should be required.

---

## 11. Authorization

Authentication answers:

> Who is logged in?

Authorization answers:

> What can this logged-in user do?

For team users:

- Role: `team`
- Access: their own team resources.
- Cannot manage other teams.
- Cannot manage organizers.
- Cannot manage admins.
- Cannot change their role.
- Cannot impersonate other users.

For organizer users:

- Role: `organizer`
- Can perform registration/team-management operations defined by the organizer permission set.
- Cannot create admins.
- Cannot create organizers.
- Cannot change roles.
- Cannot impersonate users.

---

## 12. Magic Link

Magic link is NOT part of the login flow and must not be implemented.

The authentication flow is exclusively:

```text
Username + Password
```

---

## 13. Account Lifecycle

```text
Registration submitted
        |
        v
PENDING
        |
        | all member emails verified
        | organizer approves
        v
APPROVED
        |
        v
Team account provisioned
        |
        v
ACTIVE
        |
        +--------------------+
        |                    |
        | password reset     | organizer disables/removes
        v                    v
ACTIVE                 DISABLED/BANNED
                             |
                             v
                       Login rejected
```

A rejected registration never reaches ACTIVE.

A team that is later withdrawn/removed must not remain able to log in.
