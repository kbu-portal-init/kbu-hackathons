# Registration Flow

## Purpose

This document defines the registration, student-email verification, organizer approval, and team-account provisioning flow for the KBU Hackathons system.

AI coding agents should treat this document as the source of truth for the business flow unless the repository contains a newer explicit decision.

---

## 1. Core Concepts

There are three separate concepts:

1. **Team registration**
   - A team submits its team name and member information.
   - A registration starts as `PENDING`.

2. **Student email verification**
   - Every team member must verify their own student email.
   - This proves control of the submitted student email.
   - This is NOT the same thing as logging into the team account.

3. **Team account**
   - One Better Auth user/account represents the whole team.
   - All members of the same team use the same team username and password.
   - There is one team account per team, not one auth account per TeamMember.

---

## 2. Registration Submission

When a team submits registration:

1. Validate the registration data.
2. Create the `Team`.
3. Create all `TeamMember` records.
4. Create the `Registration` with status `PENDING`.
5. Generate a verification token for every TeamMember.
6. Store only the hashed verification token.
7. Send a student-email verification email to every member.

Important:

- Registration submission does NOT create the Better Auth team account.
- Registration submission does NOT approve the registration.
- Registration submission does NOT send a team login password.
- Registration submission does NOT automatically log the team in.

---

## 3. Student Email Verification

Each member receives a verification email.

The verification link uses the application's custom `StudentEmailVerification` flow.

When a member clicks the link:

1. Validate the token.
2. Check expiration.
3. Mark the token as verified.
4. Set `TeamMember.studentEmailVerifiedAt`.
5. Record an appropriate audit event if required.
6. Return a successful verification result with `verified`, `allVerified`, and `alreadyVerified`.

The verification endpoint must NOT:

- Create a Better Auth user.
- Approve the registration.
- Create a team password.
- Send a team activation/login link.
- Automatically approve the team.

The system must not approve a registration merely because the last member verified their email. Approval always requires an explicit organizer action.

### Manual organizer verification

An organizer may manually verify a member when necessary.

Manual verification must:

1. Mark the member as verified.
2. Record who performed the action.
3. Record an audit log entry.

The organizer must still manually approve the registration afterward.

---

## 4. Approval Requirements

A registration may be approved only when:

- The registration exists.
- The registration is currently `PENDING`.
- Every TeamMember has a verified student email.
- The organizer explicitly approves the registration.

The system must not approve a registration merely because the last member verified their email.

### Approval sequence

Recommended sequence:

```text
PENDING
   |
   | all members verified
   v
Organizer reviews registration
   |
   | Approve
   v
APPROVED
   |
   v
Provision team account
```

The approval operation should be idempotent and safe to retry.

---

## 5. Team Account Provisioning

When an organizer approves a registration, the system provisions the team account.

The account represents the entire team.

### Username

The username is generated server-side from the submitted team name.

The username:

- Is generated by the server.
- Must be unique.
- Is not user-editable.
- Is not changed through a normal team profile feature.
- Should have deterministic collision handling.

Example:

```text
Team name:
KBU AI Builders

Generated username:
kbu-ai-builders
```

If the generated username already exists, use a deterministic unique suffix, for example:

```text
kbu-ai-builders-2
```

Do not silently change the team name stored in the registration.

---

## 6. Password

The team uses a single password.

All team members share:

```text
username + password
```

The initial password should be generated server-side rather than manually chosen by an organizer unless the product UI explicitly supports organizer-entered passwords.

Do not store plaintext passwords in the application database.

Use Better Auth's password/account APIs for credential management.

---

## 7. Better Auth Account Creation

The team account is created via `auth.api.signUpEmail()` during organizer-controlled provisioning.

Conceptually:

```text
Organizer approves registration
        |
        v
Validate registration
        |
        v
Create Better Auth user (signUpEmail with random password)
        |
        v
Set username/displayUsername
        |
        v
Link Team.userId
        |
        v
Mark registration APPROVED
        |
        v
Send password-setup email to team leader
```

The account-creation operation must be retry-safe.

If the Better Auth user already exists (or the Team already has a `userId`), the service should detect and reconcile instead of creating a duplicate.

---

## 8. Organizer Permissions

The `organizer` role is an operational role for this application.

Organizer permissions should be implemented using Better Auth's custom access-control/role system rather than simply giving organizers unrestricted admin access.

Organizer capabilities:

- Create team accounts.
- Set team passwords.
- Reset team passwords.
- Resend account activation/information when implemented.
- View team users/members.
- Ban team members/accounts when implemented.
- Approve registrations.
- Reject registrations.
- Manually verify team member emails.
- Perform registration-management operations.

Organizer restrictions:

- Cannot impersonate users.
- Cannot change user roles.
- Cannot create organizers.
- Cannot create admins.
- Cannot promote users to organizer/admin.
- Cannot perform unrelated super-admin operations unless explicitly added later.

---

## 9. Magic Link

Magic link is NOT part of the login flow and must not be implemented.

The authentication flow is exclusively:

```text
Username + Password
```

---

## 10. Registration Rejection

If an organizer rejects a pending registration:

- Set registration status to `REJECTED`.
- Store the rejection reason/notes when supported.
- Create the appropriate review record.
- Create an audit log entry.
- Notify the team when notification functionality exists.

If no Better Auth account has been provisioned yet, no login account should exist.

A rejected registration should not be able to authenticate as a team.

---

## 11. Withdrawal / Removal

The system currently does not have an approved-team removal feature.

If a team is later withdrawn or removed after account provisioning:

```text
Team becomes inactive/withdrawn
        |
        v
Disable or ban the team account
        |
        v
Existing sessions are revoked
        |
        v
Future username/password login fails
```

Do not permanently delete the Better Auth account by default.

Prefer a reversible disabled/banned state so audit history remains intact.

The exact implementation should use the application's chosen account-status mechanism.

---

## 12. Team Member Changes

Current product rules:

- Team members share one team account.
- A member cannot become the team leader through the authentication system.
- Team name cannot be changed through the current feature set.
- Team username is not user-editable.
- There is no member-to-leader promotion flow currently.

Any future leader-change feature must explicitly define how the team's authentication/recovery email changes.

---

## 13. Password Reset

Password reset should be possible through the team's registered recovery email.

Recommended recovery model:

```text
Team account
    |
    +-- username/password login
    |
    +-- recovery email = current team leader email
```

For password reset:

1. User requests password reset.
2. Better Auth sends the reset email.
3. User follows the reset link.
4. User chooses a new team password.
5. Existing sessions should be invalidated where appropriate.

Password reset is different from student-email verification.

---

## 14. Important Invariants

The following must always remain true:

- One Team has at most one Better Auth team user.
- One team account is shared by all members of that team.
- Student email verification does not create an auth account.
- Student email verification does not approve a registration.
- Every member must be verified before organizer approval.
- Organizer approval is an explicit action.
- Rejected registrations cannot log in.
- Withdrawn/removed teams cannot log in.
- Team username is server-generated.
- Team username cannot be changed by the team.
- Team members cannot change the team's role.
- Organizer cannot create or promote admins/organizers.
